# Document Group Workflow Design

## Goal

Build an MVP workflow system where a workflow is a transaction-level group of standalone accounting documents. Each document keeps its own form, actions, state machine, raw files, PDFs, and completion rules. The workflow layer only defines document order, creates a shared transaction ID, tracks progress across related documents, and gathers every related document into one review/print packet.

## Core Direction

Do not build a second workflow-specific form engine for every step. The existing app already has standalone document flows such as expense requests, substitute receipts, and inventory receiving. The MVP must reuse those flows and connect them with a shared workflow transaction ID.

The mental model:

- A workflow template is an ordered list of document types.
- Starting a workflow template creates one transaction ID.
- Every standalone document created inside that workflow stores the transaction ID as a foreign key-like reference.
- A workflow step is complete when the related standalone document reaches `completed`.
- The workflow can move to the next document only after the current document is `completed`.
- The workflow packet gathers raw data, raw files, PDFs, and review state from all child documents under that transaction ID.

## Current System Context

The app is a local Node HTTP server with static HTML forms under `forms/`. Server logic lives mainly in `forms/local-server.logic.js`; pure logic lives in focused `forms/*.logic.js` files. PDF generation uses Python ReportLab scripts under `scripts/`.

Existing standalone document flows:

- Expense request: `forms/expense-request.*`, `forms/expense-requests.html`, `saveExpenseSubmission`, `approveExpenseRequest`, `scripts/generate_expense_pdfs.py`
- Substitute receipt: `forms/substitute-receipt.*`, `forms/substitute-receipts.html`, `saveSubstituteReceiptSubmission`, `approveSubstituteReceipt`, `receiveSubstituteReceiptStock`
- Inventory receiving: `forms/inventory-purchase-in.html`, `createPurchaseInMovement`, inventory report/PDF support

The workflow MVP should add orchestration and grouping around these systems. It must not rewrite the existing standalone forms into a separate duplicate workflow form.

## Document Types

MVP document kinds:

- `purchase_order`: ใบสั่งซื้อ
- `substitute_receipt`: ใบรับรองแทนใบเสร็จรับเงิน
- `payment_voucher`: ใบสำคัญจ่าย
- `goods_receipt`: ใบรับของ/ใบรับสินค้าเข้าคลัง
- `expense_request`: ใบเบิกค่าใช้จ่าย
- `cash_spend_declaration`: ใบรับรอง/คำรับรองการจ่ายเงินสดส่วนตัว
- `payee_acknowledgement`: ใบสำคัญรับเงิน/ใบรับเงินคืนค่าใช้จ่าย

Existing document flows can cover some document kinds immediately:

- `substitute_receipt` maps to the existing substitute receipt flow.
- `expense_request` maps to the existing expense request flow.
- `goods_receipt` can initially map to existing inventory purchase-in logic for stock workflows, plus a lightweight standalone document shell for non-stock service receipt.

New lightweight standalone document flows are needed for `purchase_order`, `payment_voucher`, `cash_spend_declaration`, and `payee_acknowledgement`. They can share one generic standalone document page/API as long as the stored document still has its own `documentKind`, `documentNo`, state, raw files, PDFs, and completion action. This keeps the MVP small without turning workflow into a duplicate form engine.

## Lightweight Standalone Document Shell

Use one generic shell for document kinds that do not yet have a dedicated page:

- route: `/workflow-document?documentKind=...`
- data file: `data/workflow-document.json`
- storage: `documents/YYYY/MM/<document-kind-folder>/<documentNo>_<safe-title>/`
- PDFs: generated by a shared lightweight document PDF generator
- raw files: uploaded under the document's own `raw/` folder

Supported lightweight kinds:

- `purchase_order`
- `payment_voucher`
- `cash_spend_declaration`
- `payee_acknowledgement`

The shell must still work outside workflows. When opened from a workflow, it receives `transactionNo`, `workflowTemplateId`, `workflowStepId`, and `returnTo` query params.

Number prefixes:

- `purchase_order`: `PO-YYYY-MM-0001`
- `payment_voucher`: `PV-YYYY-MM-0001`
- `cash_spend_declaration`: `CSD-YYYY-MM-0001`
- `payee_acknowledgement`: `PAR-YYYY-MM-0001`

## Standalone Document Contract

Every document type must expose enough metadata for workflow grouping:

- `documentKind`
- `documentNo`
- `transactionNo`
- `workflowTemplateId`
- `workflowStepId`
- `status`
- `statusLabel`
- `completedAt`
- `completedBy`
- `folderPath`
- `pdfFiles`
- `rawFiles`
- `summary`
- `nextAction`

All standalone document types must support a `completed` state. Existing status models may keep their current states, but they need a terminal `completed` state or a normalized adapter that reports `completed` to workflow when the document's own process is done.

Examples:

- Expense request current `approved` can transition to `completed` after accounting save/sheet sync decision is finished.
- Substitute receipt current `received` can transition/report as `completed` for stock purchase flows.
- Substitute receipt current `approved` can transition/report as `completed` for general expense flows that do not require stock receiving.

## Workflow Template

A workflow template describes only:

- template ID
- template name
- description
- ordered document kind steps
- optional Google Drive sync setting
- optional Google Sheets sync setting
- active/inactive status

It does not define every field inside every document form. Those fields remain owned by each standalone document type.

Template storage:

- `data/workflow-templates.json`

Default MVP templates should be seeded when the file does not exist.

## Workflow Transaction

Starting a template creates a workflow transaction.

ID format:

- `TXN-YYYY-MM-0001`

Storage:

- `documents/YYYY/MM/workflow-transactions/TXN-YYYY-MM-0001_<safe-title>/data/workflow-transaction.json`
- `documents/YYYY/MM/workflow-transactions/TXN-YYYY-MM-0001_<safe-title>/working-md/workflow-summary.md`
- `documents/YYYY/MM/workflow-transactions/TXN-YYYY-MM-0001_<safe-title>/pdf/`

The workflow transaction JSON stores:

- transaction number
- accounting month
- title
- selected template snapshot
- current step index
- sync settings copied from the template
- child document references
- aggregate status and history

Workflow transaction status:

- `draft`
- `in_progress`
- `completed`
- `cancelled`

Workflow step status is derived primarily from the child document:

- `not_started`: child document has not been created
- `in_progress`: child document exists but is not complete
- `completed`: child document completed
- `blocked`: previous step is not complete

The workflow layer should not invent approval states that duplicate child document approval states. It can show the child document's native `statusLabel` beside the derived workflow step status.

## Starting And Running A Workflow

User flow:

1. Open workflow template list.
2. Choose a template and accounting month.
3. System creates `TXN-YYYY-MM-0001`.
4. Workflow transaction page shows ordered checklist/progress.
5. The first document step is available.
6. Clicking "สร้าง/เปิดเอกสาร" opens the standalone document form with query params:
   - `transactionNo`
   - `workflowTemplateId`
   - `workflowStepId`
   - `returnTo=/workflow-transaction?transactionNo=...`
7. The standalone document flow saves its own data, PDFs, and raw files, including `transactionNo`.
8. When the standalone document reaches `completed`, the workflow checklist unlocks the next document.
9. After the last document is `completed`, the workflow transaction becomes `completed`.
10. The workflow transaction page shows all child documents, PDFs, raw files, and a generated packet summary.

## Relationship To Existing Standalone Flows

Standalone pages must remain usable outside workflow. When no `transactionNo` is present, current behavior should continue.

When `transactionNo` is present:

- include it in the saved payload
- include `workflowTemplateId` and `workflowStepId` when provided
- after save/approve/complete, show a link back to the workflow transaction
- list pages can optionally show a transaction badge

## Completion Rules

All document kinds must have a normalized completion adapter:

```js
normalizeDocumentWorkflowStatus(documentRecord) -> {
  documentKind,
  documentNo,
  transactionNo,
  nativeStatus,
  nativeStatusLabel,
  workflowStatus: "not_started" | "in_progress" | "completed",
  completedAt,
  completedBy,
}
```

Initial mappings:

- `expense_request`: `completed` when status is `completed`; `approved` remains `in_progress` until the implementation adds the explicit complete action.
- `substitute_receipt`: `completed` when status is `completed`; `received` can be migrated/reported as `completed` for stock receipt documents.
- New lightweight docs: `completed` after their own approval/finalize action.

Existing document status constants should add `completed` where needed. This is required so workflow can make a clear next-step decision.

## Packet And Review View

The workflow transaction page must aggregate:

- each child document number
- document kind and Thai label
- native document status
- completion state
- PDF links
- raw file links
- folder path
- sync status if available

The packet PDF is a summary/index, not a replacement for child document PDFs. It should include a table of all child documents and list raw/PDF files by document.

## Sync Rules

Template can set:

- `syncGoogleDrive`: boolean
- `syncGoogleSheets`: boolean

In MVP:

- Google Drive sync should run at workflow transaction level only after transaction completion, uploading the transaction folder or linking child folders.
- Google Sheets sync should write one summary row per completed transaction.
- Existing standalone document sync can still work, but workflow-level sync settings decide whether the grouped transaction gets synced.

## API

Add endpoints:

- `GET /api/workflow-document-types`
- `GET /api/workflow-templates`
- `POST /api/workflow-templates`
- `PUT /api/workflow-templates/:templateId`
- `GET /api/workflow-transactions/next?accountingMonth=YYYY-MM`
- `GET /api/workflow-transactions`
- `POST /api/workflow-transactions`
- `GET /api/workflow-transactions/:transactionNo`
- `POST /api/workflow-transactions/:transactionNo/start-document/:stepId`
- `POST /api/workflow-transactions/:transactionNo/refresh`
- `POST /api/workflow-transactions/:transactionNo/complete`
- `POST /api/workflow-transactions/:transactionNo/sync-drive`
- `GET /api/workflow-transactions/:transactionNo/files/:section/:fileName`

Existing standalone document endpoints must be extended to accept and return workflow relation fields.

## UI

Add:

- `forms/workflow-templates.html`: create/edit workflow templates by choosing ordered document kinds and sync toggles.
- `forms/workflow-transactions.html`: start a workflow from a template and list existing workflow transactions.
- `forms/workflow-transaction.html`: transaction progress/checklist page that links into standalone document flows.

The workflow transaction page is the main MVP screen. It should show:

- transaction ID
- template name
- sync settings
- ordered document checklist
- current active document
- child document status
- buttons to create/open each document
- locked next steps until the current child document is complete
- all related PDFs/raw files grouped by document

## Tests

Use Node's built-in test runner and existing `scripts/test.sh`.

Coverage must include:

- default templates contain the six requested use cases with the correct document order
- template save/update preserves document order and sync settings
- transaction number generation scans existing transaction folders
- starting a transaction snapshots the template and creates a `TXN-YYYY-MM-0001`
- only the first document step is available on a new transaction
- workflow relation fields are saved on expense request and substitute receipt payloads
- normalized document completion maps child document status into workflow progress
- refreshing a workflow transaction advances only when the current child document is complete
- final document completion marks transaction completed
- grouped packet summary includes child PDF/raw links
- HTML pages expose template builder, transaction starter, checklist/progress, and standalone document links

## Non-Goals

- Conditional workflow logic
- Full custom form builder
- Replacing standalone document forms
- Role-based authentication
- Partial receiving
- VAT/tax invoice workflows
- Electronic signatures beyond existing printable signature boxes
