# Shopee Custom Label Supabase Mapping Design

## Goal

ย้าย reusable Manual SKU mapping ของ Shopee Custom Label จาก SQLite ที่อยู่บน filesystem ชั่วคราวของ Cloud Run ไปเก็บใน Supabase Database เพื่อให้ mapping ไม่หายเมื่อ Cloud Run restart, redeploy หรือเปลี่ยน instance โดยคงพฤติกรรม local development และ test ที่ไม่มี Supabase ไว้ใช้งานได้

## Scope and success criteria

- เมื่อ upload PDF ใน production ระบบอ่าน mapping จาก Supabase แล้วเติม bundle เดิมให้โดยจับคู่จากชื่อสินค้าและตัวเลือกสินค้าที่ normalize แล้ว
- เมื่อกด Save ระบบ upsert bundle ของแต่ละคู่ชื่อสินค้า/ตัวเลือกสินค้าเข้า Supabase รวมทั้ง SKU และจำนวนหลายรายการใน bundle
- การ Save ยังคงเก็บ snapshot ของ job สำหรับ PDF งานนั้น และสร้าง PDF/ไฟล์ใน Supabase Storage ตาม flow เดิม
- Production ไม่ใช้ SQLite mapping เป็นแหล่งข้อมูลหลักและไม่ต้องพึ่งข้อมูล mapping ใน `/tmp`
- Local mode ที่ไม่มี Supabase ยังคงใช้ SQLite mapping ได้
- Supabase table ถูกป้องกันด้วย RLS และเปิดให้ backend service role เท่านั้นตามมาตรฐาน migration เดิม

## Architecture

เพิ่ม repository สำหรับ custom-label mapping ที่ใช้ Supabase REST API ผ่าน `createSupabaseDataRepository` โดยมี operation สำหรับอ่าน mapping ตาม normalized keys และ upsert mapping bundle แบบ conflict ที่ `(product_name_key, option_name_key)`. Flow ของ custom label จะรับ mapping loader และ mapping saver เป็น dependency; production inject Supabase repository ส่วน local inject implementation เดิมจาก SQLite.

การบันทึก job metadata ยังใช้ SQLite ชั่วคราวเพื่อให้ PDF transform ภายใน request เดิมทำงานได้ แต่ reusable mapping ต้องถูกเขียนไป Supabase ก่อนตอบความสำเร็จ. ถ้า Supabase write ล้มเหลว การ Save ต้องล้มเหลวและแจ้งให้ retry ไม่รายงานว่าสำเร็จเฉย ๆ.

## Data model

สร้าง migration ใหม่ `public.shopee_custom_label_mappings`:

- `id bigint generated by default as identity primary key`
- `product_name_key text not null`
- `option_name_key text not null`
- `product_name_display text not null default ''`
- `option_name_display text not null default ''`
- `bundle jsonb not null default '[]'::jsonb`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- unique constraint บน `(product_name_key, option_name_key)`
- RLS enabled และ revoke สิทธิ์ `anon`, `authenticated`

`bundle` ใช้รูปแบบ `[{"sku":"TOP-BLUE","quantity":1}]` และ validation เดิมยังเป็นผู้ตรวจว่า SKU ไม่ว่างและจำนวนเป็นจำนวนเต็มบวก

## Data flow

1. Upload route parse PDF และสร้าง mapping keys จากรายการสินค้า
2. Mapping loader อ่านเฉพาะ keys เหล่านั้นจาก Supabase ใน production หรือ SQLite ใน local
3. Frontend แสดง bundle ที่อ่านได้เป็นค่าเริ่มต้นให้แก้ไขได้
4. Preview render ใช้ mapping ที่ส่งจาก form แต่ไม่บันทึก reusable mapping
5. Save render PDF แล้ว upsert normalized mappings ไปยัง Supabase ใน production หรือ SQLite ใน local
6. Job snapshot บันทึก `savedMappings` ตาม flow เดิมเพื่อใช้อ้างอิงงานปัจจุบัน

## Error handling

- Supabase response ที่อ่านไม่ได้หรือเขียนไม่สำเร็จต้อง propagate เป็น operation error ของ custom label
- การ upsert ต้องใช้ `Prefer: resolution=merge-duplicates,return=representation` และตรวจว่าคู่ key และ bundle ที่ตอบกลับถูกต้อง
- ห้าม fallback ไป SQLite ใน production เพราะจะทำให้ข้อมูลกลับไปอยู่บน filesystem ชั่วคราว
- Local/test ใช้ SQLite ได้เมื่อ runtime ไม่ใช่ Cloud Run

## Testing

- Unit test repository ตรวจ URL, payload, conflict key, mapping response และ error เมื่อ response ไม่ตรง
- Unit test custom-label flow ตรวจ loader ถูกเรียกตอน upload และ saver ถูกเรียกตอน Save โดย Preview ไม่เรียก saver
- Migration test ตรวจชื่อตาราง, unique constraint, jsonb bundle, RLS และ revoke สิทธิ์
- Existing custom-label API/logic tests ต้องยังผ่านทั้งหมด
- Run syntax check, targeted tests และ full test suite ก่อน commit/deploy

## Out of scope

- ไม่เปลี่ยนรูปแบบ matching ของ mapping นอกเหนือจาก normalization ที่มีอยู่
- ไม่ย้าย job metadata หรือไฟล์ PDF ไปจาก flow ปัจจุบัน
- ไม่เพิ่มหน้าจัดการ mapping แยกต่างหาก
